# Add guardian alpha testing

Tested on 27 October 2026 using the repository Java sources through
`LogicManager`, the normal command parser, model, and JSON storage. This does
not establish that `test/Mentora.jar` contains the same implementation.
No production behavior was changed and no UI testing was performed.

## Confirmed defect: unknown text produces the wrong error

Starting from `test/data/addressbook.json`, execute:

```text
add-guardian n/Ann p/61239999 extra
```

Expected under the shared conventions in `docs/FeatureSpecification.md`:

```text
Invalid command format. Use: add-guardian n/NAME p/PHONE
```

Actual:

```text
Phone number must be an 8-digit Singapore number, optionally prefixed by +65.
```

Another unknown-text variant, `add-guardian p/61239999 n/Ann 1/value`,
produces the name constraint error rather than the shared format error.
Both commands leave the full register, saved JSON, and exact filtered student
records unchanged. Severity is limited to misleading command feedback;
no data corruption was observed.

`AddGuardianAdversarialTest.unknownTextMustUseSharedFormatError` exercises nine
commands, each with a new temporary copy of the supplied baseline and an active
`find-student n/Mei Lin` filter. It collects exact-message discrepancies while
asserting unchanged state after each command. The test intentionally remains
failing to expose the contract violation; production code was not changed.

## Structure and verification

`AddressBookParser` dispatches to `AddGuardianCommandParser`, which constructs
the name and phone value objects. `AddGuardianCommand` checks canonical phone
uniqueness and adds an immutable guardian. `LogicManager` saves the mutation and
restores the previous register on an injected storage IOException.

The targeted Gradle run selected `AddGuardianIntegrationTest`,
`AddGuardianAdversarialTest`, and `AddGuardianCommandParserTest`:
15 test methods executed, 14 passed, 1 failed. The failing method reports the
two message discrepancies above. Evidence is in `build/test-results/test/`
and `build/reports/tests/test/index.html` (regenerated by later runs).

Earlier passing integration tests cover canonical phones, duplicate names,
name lengths, case, punctuation, CJK names, whitespace, malformed parameters,
save/reload, and injected save failure followed by retry. Some earlier methods
contain multiple dependent scenarios and broad assertions; their passing count
must not be described as exhaustive coverage. In particular, not every success
case independently proves every field and relationship after reloading.

The raw-name length exceeding 80 due only to repeated spaces is consistent
with the specified limit after normalization and is not a defect.

## Remaining limits and next work

No finite test suite establishes correctness for every possible command string.
The supplied running jar has not been verified against these sources.
Unicode normalization forms, supplementary Unicode character counting,
very large inputs, storage failures after a partial write, and arbitrary
sequences of commands remain unverified. These are coverage limits, not
confirmed defects. No JavaFX/UI claims are made.

Next contributors should first resolve the exact unknown-text error contract
with the team, retain the failing regression as evidence, and improve existing
scenario isolation and assertion precision before claiming broader coverage.
